# おはなし名人：修正・機能追加指示書

作成日：2026-10-23  
対象：脚本エディタ「おはなし名人」（まずブラウザ版のみ）

## 0. 着手条件・基本方針

- **現在、使用制限によって中断している既存タスクを先に再開・完了**すること。その進行状況と変更内容を確認してから、この指示書の作業に着手する。既存作業を無断で破棄・上書きしない。
- 着手前にリポジトリの現状、既存の保存形式、編集画面、縦書きレイアウト、貼り付け・改行処理、選択範囲からの章作成・章削除処理、バックアップJSONの保存・読み込み・ファイル選択処理、PDF/印刷処理、アプリ起動時のサンプル／既存データ復元処理、スマホ用サイドバー、Undo/Redo履歴・タッチイベント、テスト、デプロイ方法を調査する。
- ここに示す実装案が現行アーキテクチャに適合しない場合は、**目的・データ保全・互換性を優先して方法を修正**する。原因や設計上の重要な問題が見つかった場合は報告する。
- **既存の脚本・章・本文を消去、破損、誤結合、意図しない別カットへの置換をしない**。保存形式を変更する場合は既存データの読み込み互換性と移行・復旧方法を確保する。
- 変更の優先順位は①改行・書式不具合および④章への移動時の書式崩れを調査・修正 → ②自動カット管理 → ⑥スマホのJSON読み込み対応、⑦起動時の空白原稿、⑧モバイルのサイドバー操作、⑨タッチUndo/Redo → ③PDF直接保存・⑤削除時のバックアップ任意化。依存関係や既存実装に応じて順序を調整してよい。
- 今回は**おはなし名人のみ修正**する。「プリプロ名人」は変更せず、将来の安全な連携に備えた設計・形式を整える。
- 各機能を実装・検証後、動作内容、注意事項、テスト結果を簡潔に報告する。**ブラウザだけで試せる公開・プレビューURLを更新のたびに提示する**。デプロイが失敗した場合は成功したと称さず原因を報告する。

## 1. 改行・列間隔の異常拡大と「自動修正」

### 再現した操作

1. 別アプリで作った `.txt` の本文を Chapter 1 に貼り付ける。
2. Chapter 1 の内容を Chapter 2 にコピー＆ペーストする。
3. その内容をカットして Chapter 3 へペーストする。
4. 章を移動して貼り付ける操作を繰り返す。

### 現象

縦書き画面で、繰り返すほど文字列の列と列の間隔が極端に広がる。Chapter 4〜5 で特に顕著。手動では正常化できない。

### 要件

- 原因を切り分けること。**余分な改行・空行の蓄積**なのか、**HTML/リッチテキストや段落要素の重複**なのか、**CSS の行・列レイアウト**なのか、その他の要因なのかを検証する。見た目だけを無理に詰める対症療法にしない。
- TXT貼り付け、通常のコピー、カット、同一章内・章間の貼り付けを繰り返しても、列間隔や本文構造が崩れないようにする。
- 既存の「自動修正」に、**異常に増殖した空行・改行を正常化する機能**を加える。すでに崩れた本文も修復対象とする。
- **意図的に挿入した空行を必ず保持する必要はない**。ただし、文章そのもの、語順、セリフ、ト書き、章、カット境界を壊さない。
- 後述の「Enter 2回によるカット分割」と衝突しないよう、カット境界と不要な空行を内部的に区別する。既存データを一律に空白で分割して誤認識しない。

### 確認項目

- TXT→Chapter 1→2→3→4→5 と移動しても列間隔が一定。
- 「選択範囲を章に」で作成した章でも、元の柱・ト書き・セリフ等の区別とレイアウトが維持される（第4項を参照）。
- すでに異常のある本文に「自動修正」を適用すると正常化し、本文は失われない。
- 編集、保存、ページ再読み込み、再編集でも再発しない。

## 2. ラフ執筆向けカット自動生成・自動採番

### 目標

脚本をラフに書く段階で `#C1`、`#C2` … を手作業で入力・振り直ししなくても済むようにする。

### UI・動作要件

- **Enter 2回による区切り操作**で新しいカットを作れるようにする（既存の段落編集・縦書き入力・日本語IME入力と干渉しないように設計）。
- カット番号は編集画面に `#C1`、`#C2`、`#C3` … のように**常に欠番のない連番**で自動表示する。`C1A` のような枝番号は使わない。
- カットを途中に挿入・削除・移動すると**表示番号のみ自動で振り直す**。作品全体の通し番号とし、章をまたぐ順番にも対応する。
- **不変の内部カットID**を各カットに持たせ、表示番号と分離する。表示番号が変わっても同じカットと識別できること。通常画面に内部IDを表示する必要はない。
- 保存・再読み込み後も、各カットの内部ID・本文・所属章と順序が保持されること。
- 既存の `#C番号` を含む脚本/TXTの取り込みや過去の保存データを壊さず、適切に移行・認識できること。重複番号・欠番・空カットなどの扱いを明確にする。
- 「自動修正」は**正式なカット境界を消去しない**。外部TXTに含まれる連続改行は既存の編集データと同様に無条件でカットに変換しない。貼り付け時のカット変換ルールを安全に設計する。

### プリプロ名人との将来の連携に関する制約

- 将来、プリプロ名人のタイムライン上の画像・音声・尺などが**間違ったカットに紐づく事態を絶対に避けたい**。
- 連携は表示番号だけに依存させず、内部カットIDと対応づけられるデータ形式を想定する。
- ただし現状のプリプロ名人が内部IDを受け取れるとは限らないため、**今回の実装だけで両アプリの連携が安全になったとは判断しない**。
- 現在の TXT / Markdown 書き出しは汎用テキストとしての用途を保つ。IDを受け渡すには将来的に専用の構造化データ形式や対応表などが必要か調査し、今回どこまで準備したか説明する。
- プリプロ名人側の受け入れ対応が完了するまで、番号変更後の脚本を既存Vコンに**自動で誤対応づける連携は行わない**。

### 確認項目

- C1 / C2 / C3 の C1 と C2 の間に新規カットを挿入すると、画面上は C1 / C2（新規）/ C3（旧C2）/ C4（旧C3）となる。
- 旧C2・旧C3の内部IDと本文は変化しない。削除・移動・章またぎでも同様。
- 多重改行、貼り付け、カット移動、Undo/Redo、保存・再読み込み、日本語IMEの変換操作を確認する。

## 3. 「PDFに保存」で印刷ダイアログを開かず直接ダウンロード

### 現状

「作品を書き出す」の「PDFに保存」と「印刷」のどちらを押しても同じブラウザ印刷ダイアログが開く。

### 要件

- **「PDFに保存」**：ブラウザの印刷ダイアログを出さずにPDFを生成し、直接ファイルをダウンロードできるようにする。
- **「印刷」**：これまでどおりブラウザの印刷ダイアログを開く。
- 現在のPDF用レイアウトとオプションを維持する：**A4横・縦書き・ページ番号付き・表紙を付けるチェックの選択**。
- 日本語フォント、縦書き方向、文字欠け、禁則・改行、改ページ、長い章、複数章などを検証する。
- PDFの生成手段は現行コード・利用環境を見て選定する。印刷ダイアログなしで同等品質を維持できない場合、安易に品質を落とさず技術的な制約と代替案を報告する。
- TXT / Markdown の既存書き出しを壊さない。

### 確認項目

- 「PDFに保存」で `.pdf` を直接取得できる。印刷ダイアログは開かない。
- 「印刷」で従来の印刷ダイアログが開く。
- 表紙オン/オフ両方で正常に出力され、本文・章・ページ番号などに欠落がない。

## 4. 「選択範囲を章に」で新しい章を作ると書式が崩れる

### 再現手順・観測

1. 既存の章（例：Chapter 5「ラストシーン」）で、縦書き本文の一部を選択する。
2. 上部の「選択範囲を章に」を押し、「選択範囲から章を作成」ダイアログで新しい章を作る。
3. 新規の章（例：Chapter 6）に移動した選択部分の、**柱・ト書き等の書式と縦書き配置が元と異なる**。柱とト書きが不自然に詰まり、縦書きの列・改行構造が崩れる。**「自動修正」を押しても直らない**。
4. 再現動画：`画面録画 2026-10-23 174002.mp4`（指示書と併せてCodexに提供されていれば確認すること）。

### 要件

- 「選択範囲を章に」は、**本文文字列だけでなく、元の段落種別・構造（柱／ト書き／セリフ）と適切な区切り**を保ったまま選択範囲を新章へ移動する。
- 選択範囲の開始・終了が段落の途中である場合も、元章に残る部分と新章に移る部分が壊れないよう扱う。本文の欠落・重複・順序の入れ替わりを起こさない。
- 見た目の問題だけでなく、内部の文書構造・シリアライズ／デシリアライズ・選択範囲分割処理・縦書きCSSのどこで破損するかを調査して修正する。
- 移動後も通常の編集、コピー＆ペースト、保存・再読み込みが正常に機能する。
- **「自動修正」でも既存の不正な空行や修復可能な書式異常を是正**できるよう検討する。ただし、失われた段落種別を確実に推定できない場合に、勝手に別の種別へ変更しない。まず不具合の再発防止を優先する。
- 第2項で導入する自動カット管理後は、選択範囲内のカットIDの扱いを明確にし、既存カットのIDが意図せず再生成・複製されないようにする。

### 確認項目

- 柱、ト書き、セリフ、改行を含む選択範囲を章に移しても、内容・書式・縦書きレイアウトが維持される。
- 段落途中・複数段落・複数カットの選択を試し、移動元・移動先の双方に欠落、重複、不正な余白が発生しない。
- Undo/Redo、保存・再読み込み、自動修正を確認する。

## 5. 章を削除するとき、バックアップ保存を任意にする

### 現状

章の削除操作時にバックアップの取得が必須になっており、不要な場合にも毎回バックアップを保存しなければ削除できない。

### 要件

- **バックアップを保存せず、そのまま章を削除できるようにする**。バックアップの保存を削除実行の必須条件にしない。
- 誤操作防止の削除確認は維持する。例：「バックアップを保存する」のチェックを任意にし、未チェックでも「削除」を実行できるようにする。または「バックアップして削除」「バックアップせず削除」を分ける。最終UIは既存画面と整合させて選定する。
- バックアップしたいユーザー向けの既存保存機能は引き続き利用できること。キャンセルで何も変更しない。
- **選択した章だけを削除**し、別の章の本文や進捗情報が壊れないようにする。削除後の章番号・総文字数・進捗表示などの更新を確認する。
- バックアップを保存しなかった場合に、保存していないのに「バックアップ済み」と表示しない。削除の取り消し可否が現状どうなっているかを確認し、利用者に誤解を与えない。

### 確認項目

- バックアップなしで章を削除できる。
- 必要な場合は従来どおりバックアップを保存して削除できる。
- キャンセル時は章・本文とも不変。削除後も他の章を正しく編集・保存できる。

## 6. スマホでDropbox保存のバックアップJSONを選べない

### 現状・再現状況

- おはなし名人のスマホ版で、Dropboxに保存したバックアップ `.json` を「原稿を開く」などのファイル読み込み操作から選択しようとしても、JSONファイルが**グレーアウトして選択できない**。
- スマホのOS、ブラウザ、ファイルピッカー、Dropboxとの連携状態は未確認。**原因を断定せず**、まずファイル選択制限とバックアップ形式を調査する。

### 要件

- **PCで作成した既存のバックアップJSONを、スマホから読み込める**ようにする。スマホで保存したJSONもPCで開けるよう、保存形式の互換性を維持する。
- Android（Chrome等）・iOS（Safari等）で、スマホ本体に保存された `.json` を選択・復元できること。
- DropboxにあるJSONを、OSのファイルピッカーや連携済みファイルプロバイダーを通して選択できる場合には、そのまま読み込めるようにする。**ブラウザ／OSの制約でクラウド上のファイルを直接選べない場合**は、Dropboxから端末にダウンロードして読み込む手順を案内する。DropboxのAPI連携・アカウント認証を新規実装することは今回の必須要件ではない。
- `<input type="file">` の `accept` 指定、`.json` 拡張子、`application/json` やプロバイダーごとのMIMEタイプ、モバイルのファイルピッカーの挙動を調べる。必要に応じてファイルを選択できる範囲を広げても、**実際の内容をJSONとして厳密に検証**し、異なる形式・破損データは安全に拒否する。
- 読み込む前にバックアップJSONの内容・形式を検証する。既存原稿を上書きする可能性がある場合は、内容が消えることのないよう確認や安全な読み込みフローを設ける。エラー時は既存データを維持する。
- 既存のPC版の読み込み、JSONの書き出し、章・カット情報、将来の内部カットIDの保存を壊さない。

### 確認項目

- **Android と iPhone**で、ローカルに保存した正常なバックアップJSONを選択し、原稿を復元できる。
- DropboxからOSのファイルピッカー経由で選べる端末・環境では、該当JSONがグレーアウトせず読み込める。選べない環境では端末に保存後の読み込みが動作する。
- 拡張子の大小文字やMIMEタイプの揺れがあっても有効なバックアップを安全に判定できる。
- 不正JSON、別アプリのJSON、不完全なバックアップ、読み込みキャンセルで既存原稿が壊れない。
- スマホから開いた後の編集・保存・再読み込みと、PCとの往復を確認する。

## 7. 起動時にサンプル「余白の向こう」を自動で開かない

### 現状

アプリを起動すると、サンプル作品「余白の向こう」が自動で開かれる。ユーザーは最初からまっさらな原稿を書き始めたい。

### 要件

- **新規利用時や新しい原稿の開始時の初期状態は、サンプル本文のない空白原稿**にする。サンプル「余白の向こう」を自動生成・自動表示・本文へ挿入しない。
- アプリの現行仕様に応じて新規原稿の最低限の構造（例：空の第1章）が必要なら維持してよいが、**作品タイトル・本文などにサンプル文言を入れない**。
- **既存ユーザーの保存済み作品・自動保存データを初期化／上書きしない**。従来の再開・復元導線がある場合は維持し、サンプルの自動表示のみを廃止する。起動時の復元条件が不明なら先に現状を確認してから設計する。
- サンプルをユーザー自身が開ける機能は残して構わないが、その場合も明示操作でのみ開く。

### 確認項目

- 新規ブラウザ環境で初回起動時、サンプルは開かず、空白から入力を開始できる。
- 既存の保存済み作品を持つ環境で、作品が消えず以前どおり開ける。
- ページ更新、端末再起動、保存／復元後も既存原稿が意図せずサンプルや空白原稿で上書きされない。

## 8. スマホでエディタ部分をタップしたらサイドバーを閉じる

### 現状

スマホ表示でサイドバーを開いているとき、エディタ領域をタップしてもサイドバーが閉じない。

### 要件

- **スマホのサイドバーが開いている状態で、その外側のエディタ領域（または背面のオーバーレイ）をタップするとサイドバーを閉じる**。
- 閉じるボタンやメニューからの開閉は従来どおり動作させる。
- 閉じるためのタップが**本文の誤入力・選択解除・意図しないカーソル移動**などを引き起こさないようにする。必要なら最初のタップは「閉じる」のみに使い、次のタップで編集を開始できるようにする。
- サイドバー内部のボタンやスクロール操作では意図せず閉じない。PCの通常レイアウトを変えない。

### 確認項目

- スマホでサイドバーを開く → エディタ側の見えている領域をタップ → サイドバーが閉じる。
- サイドバー内の章選択・スクロール・閉じるボタンは正常動作する。
- 画面回転・狭い幅での操作やタップ後の本文編集に支障がない。

## 9. スマホで二本指タップ＝Undo、三本指タップ＝Redo

### 要件

- **スマホ上のエディタで、二本指の同時タップで元に戻す（Undo）、三本指の同時タップでやり直し（Redo）**を実行できるようにする。
- 本文の入力、削除、貼り付け、書式編集、カット／章の移動・作成など、既存のUndo/Redoが対象とする編集履歴と矛盾しないよう、アプリの履歴管理に接続する。未対応の操作を「取り消せる」と誤認させない。
- タップとスワイプ／スクロール／ピンチズーム／複数指の長押しを判別し、**意図しないUndo/Redoやズーム操作の破壊を避ける**。二本指・三本指を数えるだけでなく、短時間・移動量などの判定を設け、1ジェスチャーにつき1回だけ実行する。
- 日本語IMEの変換中や入力欄・ダイアログ操作中に不適切な取り消しが起こらないようにする。必要ならエディタに操作対象を限定する。
- iOS Safari／Android Chrome等では**OS・ブラウザ標準の複数指ジェスチャーと競合する可能性がある**ため実機動作を検証する。ブラウザ側がイベントを渡さない環境では実現可能性・制限を明記し、既存のUndo/Redoボタンやキーボードショートカットを使える状態にしておく。ブラウザのズームやアクセシビリティ機能を無理に停止しない。
- キーボードの Ctrl/Cmd+Z、Redoショートカット、既存の編集UIを退行させない。

### 確認項目

- スマホで文字入力後、二本指タップ1回で直近の編集が1段階戻る。
- その後、三本指タップ1回で同じ編集が1段階やり直される。
- 編集履歴がない状態や、取り消し後に新規編集した状態でも安全に動く。
- スクロール・ピンチズーム・テキスト選択・日本語入力・サイドバー操作で誤発動しない。
- **この二本指Undo／三本指Redoは、今後作るほかのブラウザアプリにも共通で採用したいユーザー方針**。ただし本指示書でコード変更するのは「おはなし名人」のみ。別アプリには個別の改修時に適用する。
