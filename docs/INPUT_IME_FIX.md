# 削除・日本語入力の緊急修正（2026-10-24）

## 再現と原因

提供された2本の録画を参照した。録画と原稿は公開リポジトリに含めない。

- 単文字の通常削除は検証用Chromeで動作した。一方、編集不可のカット番号を含む全選択では削除が止まった。エディタに有効なカーソルがない状態では、Ctrl+Aがページ全体を選択する場合もあった。
- 空段落の `<br>` の後ろにカーソルを置き、Chromeのネイティブcomposition経路で `ｔ → て → てｓ → てす → てすｔ → てすと → テスト` を送ると、`ｔテスト` になった。アプリのイベントを外した最小contenteditableでも再現し、改行要素の前では `テスト` となった。2件には別々の修正を行った。

## 変更

- 全選択を原稿内に限定し、カット番号を原子的な境界として範囲削除する。全削除後も1つの内部編集枠と入力用段落を保持する。境界だけを削除する場合は前後の本文を残す。
- 通常の文字削除・単語削除はブラウザに任せ、範囲削除とカット境界だけを補う。ソフトキーボード用beforeinput経路も対応する。
- フォーカス、末尾移動、書式変更、履歴復元で、空段落の改行要素より前にカーソルを置く。変換中は位置を変更しない。
- composingフラグとイベントのisComposingを併用し、変換中のcaptureを抑止する。不要なクラス変更・番号DOMの書き直しを減らす。縦書き、縦中横、手動書式、履歴、保存形式は維持する。

## 検証

- `tests/input-ime.py`: 110項目。PC／スマホ相当の画面幅、縦書き／横書きで、Backspace・Delete・範囲／全体削除・カット境界・Undo／Redo・再読込とID保持を確認。
- Chromeのネイティブcomposition経路で「テスト」「こんにちは」「きょうはいいてんきです」および「今日はいい天気です」への候補更新・確定、改行後、全削除後、途中挿入を確認。変換途中の保存状態は変えず、1回の確定として履歴に記録する。
- 既存ブラウザ54、追加82、書式36、公開後受入59項目とNodeチェックが合格。ログは [test-results/input-ime](test-results/input-ime)。

この自動試験は実際のOSのローマ字入力・候補ウィンドウを操作しない。Windows／macOSのIME候補選択とEnter確定、iPhone／Android実機、Safariは未確認。スマホ相当の画面幅・タッチ設定と、beforeinputのみの削除イベントは確認済み。実機で同じ連続入力と削除を確認する必要がある。
