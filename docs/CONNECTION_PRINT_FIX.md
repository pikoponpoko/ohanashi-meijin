# 通常ブラウザの接続復旧とPDF・印刷の番号上揃え

2026-10-24（JST）。公開URLは通常ブラウザで `ERR_FAILED`、シークレットでは開くと利用者から確認を得た。Cloudflare APIでは公開有効・配信100%で、Cloudflare Accessも有効ではなかった。通常プロファイルのPWA状態や拡張機能などが候補で、利用者端末での確定原因は未特定。

## 接続の復旧

旧Service WorkerでCacheStorageの読み取りが拒否されると、応答Promiseの拒否がナビゲーションへ伝わり、Chromeの `ERR_FAILED` を再現できた。新しいworkerはキャッシュの例外を捕捉してオンライン取得へ戻る。キャッシュもネットワークも利用できないときは、原稿を変更しない接続案内を返す。従来のキャッシュ済みオフライン起動と、失敗した更新で旧シェルを残す動作は維持する。

通常の編集シェルとは独立した [復旧ページ](https://ohanashi-meijin.pikoponpoko.workers.dev/recovery.html) を追加した。このパスと専用JSは古いworkerのシェル対象に入っていないため、旧ナビゲーションキャッシュの例外を通らず開ける。通常ブラウザの新しいタブで使う。

1. 他の画面で編集中なら、保存して閉じる。
2. 「原稿を保存」で現在の生JSONをダウンロードする。
3. 保存完了を確認して「保存を確認して接続を修復」を押す。

復旧は同一アプリのルートスコープに登録されたService Workerだけを解除し、アプリを開き直す。原稿の保存キー・退避原稿・他のlocalStorageは削除も書換えもしない。サイトデータ全体の削除は行わない。読み取りが拒否されている場合や、別画面が原稿を更新した場合は修復を進めない。

これは実際の利用者プロファイルでの回復を確認済みという意味ではない。復旧ページ自体も開かない場合は、拡張機能や通常プロファイルのアクセス制御など、Service Worker以外の調査が必要。利用者にはデータ削除を指示しない。

## PDF・印刷のカット番号

カット番号を生成する段落にも、以前はト書きの `.action { padding-inline-start: 3em }` が適用されていた。エディタの `.cut` は上揃えだったため、PDFと印刷だけが下がっていた。

構造上の境界に専用の `.cut` を指定し、組版計測・PDF・ブラウザ印刷のすべてで `padding-inline-start: 0`、`text-indent: 0` とした。ト書きの3字下げ、本文のフォント・サイズ、原稿の文字列・書式・カットIDは変更しない。印刷と直接PDFは同じ段落を使う。

## 検証

- Node全チェックと追加のキャッシュ失敗試験が合格。
- Chromeで旧workerの `ERR_FAILED` を再現→復旧ページ→生JSON保存→再接続の7項目が合格。本文・ID・退避原稿・他の保存値を保持した。
- 3書体のPDF・印刷で18項目が合格。番号の上端配置とト書きの字下げを別々に確認し、原稿不変を確認した。
- PWA更新・オフライン・失敗復旧の既存15項目が合格。
- ログは [test-results/connection-print](test-results/connection-print)。合成PDFの画像は [screenshots/cut-top](screenshots/cut-top)。

利用者端末での通常ブラウザの復旧、実機の印刷ダイアログ・iOS／Android・実IMEは未確認。原本を使った新しいPDFは公開リポジトリ外に保存する。公開結果と配信版はPR説明に追記する。
