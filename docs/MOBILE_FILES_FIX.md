# スマホのJSON選択・作品切替の修正

対象：Galaxy Z Fold8、ChromeからインストールしたWebアプリ。
報告画像では約57KBの `.json` がファイル提供元で「BIN file」と判定され、選択不可だった。

## 変更

- ネイティブの「開く」からMIME・拡張子フィルターを除去。BIN/octet-stream扱いのJSONも選べるようにし、読込後に形式を検証する。HTMLファイル入力もaccept制限を設けない。不正JSON・非対応形式では元原稿を変更しない。
- TXT/MDの「開く」を別作品への切替に統一。従来の章追加では、同じTXTを開くたびに章・カットが増えていた。元の作品は「保存した原稿」に残し、新しい作品の番号は1から開始する。表示・推定尺の設定は引き継ぐ。
- 旧処理は、現在原稿の検証・退避・新原稿のlocalStorage保存のどれかで失敗すると新規作成もJSON切替も中止した。破損した編集中データも、そのままのJSONと最後の保存済みJSONを退避してから切り替える。
- localStorageが容量上限の場合は、IndexedDBの同一トランザクションに退避原稿と新しい編集中原稿を保存する。両方の保存先が失敗した場合は切替を中止する。既存localStorage・原稿・設定・退避データは削除しない。
- 追加保存先の原稿を起動時に復元するまで入力を止める。保存成功前に「保存済み」と表示しない。作品切替中の古い自動保存が新作を上書きしないよう保護する。
- 「保存した原稿」で両方の保存先を扱う。過去の日時メタデータが欠けた退避も保持・表示する。
- 独立した接続修復ページも追加保存先の最新原稿を書き出す。保存後に別画面で原稿が更新された場合は修復を止める。旧Service Workerの退役方針は継続する。

端末の保存領域を直接調査できていないため、新規作成失敗の端末上の直接原因は未確定。
容量不足と不正な編集中データの両経路を専用プロファイルで再現・検証した。

## 保存先と切戻しの注意

通常は既存のlocalStorageキー・v2形式を維持する。追加保存先は同一オリジンの
IndexedDB `ohanashi-manuscripts-v1` / `records`。`active` に最新JSON、`archive:*` に退避を保持する。
追加保存先へ切り替わった後もlocalStorageの元データは残す。以降の保存・再起動・修復では追加保存先を優先する。

この形式を利用した端末に旧実装を単純配信すると、古いlocalStorage原稿だけが表示される可能性がある。
問題が起きた場合は追加保存先を理解する版で前進修正し、最新JSONを書き出す。サイトデータ削除・古い版への単純な切戻しは行わない。
プレビューと本番は保存領域が異なる。試験はユーザーのブラウザプロファイルを使わず実施した。

## 検証

`npm test`、Chromiumでのモバイルファイル専用試験、編集・PDF54項目、リリース82項目、
TXT34項目、使用操作66項目、フィードバック59項目、集中表示28項目、SW退役23項目、修復7項目を確認。
専用試験には実際のlocalStorage上限までの書込、全キー値保持、DBの片側書込失敗時のロールバック、
再読み込み・退避復元・修復JSONの最新性を含む。OSファイル選択はAPI引数と選択結果を模擬している。
Galaxy実機のファイル選択画面は利用者による再確認が必要。
