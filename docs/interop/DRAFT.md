## 確定済みの基本方針

ユーザーの2026-10-24の回答を前提とする。

1. ファイル経由の「おはなし名人 → プリプロ名人」一方向連携。
2. 章・シーン・カット・柱・ト書き・台詞・話者・OFF・ナレーションを版付きJSONで渡す。
3. 永続カットIDで対応し、表示番号の変更に依存しない。
4. 受信側で追加・削除・移動・本文変更を検出する。
5. 新規カットには空の絵のプレースホルダーを作る。
6. 既存の絵・音声・尺・カメラ等は勝手に削除・変更しない。
7. 差分プレビュー・手動確認を経て確定し、Undoできること。
8. ト書きの改行は個別動作単位。柱や台詞の折返しを絵変わりにしない。
9. AI/APIは曖昧な内容の任意の補助であり、必須にしない。

## フィールド案

[JSON Schema案](ohanashi-prepro.schema.json)、[基準サンプル](samples/baseline.json)、[更新サンプル](samples/revised.json)、[期待差分](samples/expected-diff.json)を添付。JSON Schema draft 2020-12を使う。交換形式の提案番号 `0.1-draft.1` は既存保存v2や `.vconte` v1と別。

| フィールド案 | 意味・保持規則 |
|---|---|
| `format/schemaVersion` | 形式識別子と厳密な版。未知の版・draftは自動適用しない。正式化時の後方互換は要合意。 |
| `source.app/documentId` | 送信元と作品の永続ID。現行おはなしには作品IDがないため、生成・保存・複製・バックアップ復元の方法を要合意。タイトルや内容ハッシュを作品IDにしない。 |
| `source.revision` | 同じ作品の書出しリビジョン案。採番・復元後の分岐は未確定。番号だけで最新と判定しない。 |
| `chapters[].id/title/cuts` | 既存の章ID・タイトル・配列順。章の並替えとカットの章間移動を区別。 |
| `cuts[].id/displayNumber/blocks` | 既存の永続カットID、表示専用通し番号、順序付き本文。番号は照合キーにしない。空カットはblocksが空のまま保持。 |
| `blocks[].kind/raw` | `sceneHeading/action/dialogue/text/blank`。元の論理行・改行をrawに残す。台詞内の折返しはraw内の改行、動作単位は別actionブロック。空行はblank。 |
| `blocks[].scene` | 柱に対応する `heading` と任意の `location/time`。曖昧ならheadingとrawのみ渡す。シーンはカット横断の文脈であり、新しい絵/カットの境界ではない。 |
| `blocks[].speaker/delivery/text` | 話者名、`normal/off/narration/unknown`、台詞本文。話者と区分は分離。人物を名前一致だけで自動統合しない。受信側kindとの対応は要合意。 |
| `blocks[].interpretation` | `explicit/heuristic/unresolved`。明示情報と推定を区別し、曖昧なものは手動確認する。AIなしでもrawで確認可能。 |

現行の行番号は編集で変わるため永続台詞IDにしない。ブロック/シーンに永続IDを持たせるかは未確定。案はカット単位の本文差分を表示する最小範囲で、台詞ごとの自動マージを約束しない。既存台詞への対応が曖昧なら、タイミングを維持して手動確認する。sceneHeadingにsceneを必須、dialogueにspeaker/delivery/textを必須とする案である。他のkindに付加した解釈フィールドを許容するかも正式化前に決める。

## ID対応と差分案

受信側に `(source.app, source.documentId, sourceCutId) → targetCutId` の対応表と前回適用した送信スナップショットを保存する案。受信側の既存IDを送信IDで置換しない。別作品なら同じcutIdも別の出典。既存作品への初回対応は手動で確定し、表示番号・タイトル・台詞の一致のみで対応を作らない。

1. ファイルを別領域で読み、サイズ・版・スキーマ・ID一意性を検証する。未知の版や重複章/カットIDは適用前に拒否。文字列をHTMLとして実行しない。
2. 前回送信と新ファイルをIDで比較。追加・欠落・章間移動・本文変更・表示番号のみ変更を分ける。相対順の変更は、両ファイルに残る既存カットだけで判定する案。途中への追加だけで後続すべてを「移動」と扱わない。同一ファイルの再読込は変更なし。
3. 受信側現在状態と前回適用状態も比較し、双方変更なら競合として保留。古い/分岐ファイルを自動適用しない。
4. 新規カットは受信側IDと空の絵プレースホルダーを作る。仮尺は受信側の設定で確認し、本文から既存尺を自動変更しない。
5. 送信側で消えたカットは「削除候補」。素材付きカットは既定で保持。移動による絶対タイムラインの変化もプレビューし、相対オフセット・音声・カメラは勝手に変更しない。
6. 本文変更は既存の絵・音声・尺・タイミング・カメラと分離。台詞の対応が曖昧なら既存台詞・アンカーを保留して変更候補を提示。
7. 選択した差分を一括トランザクションで確定。1回Undo/Redoで対応表・前回スナップショット・作品データも復元。キャンセル・途中エラーは全て不変。

JSON SchemaだけではID一意性、全章通し番号、ID対応の正当性を検証できないため、意味検証も必要。サンプル検証はアプリの差分エンジン/受信機能の実装を意味しない。

## 統合受入条件（実装後）

- 旧保存v1/v2の章・カットIDと原稿を保持。作品ID追加の移行は元データを退避し、保存失敗で原稿を失わない。
- baseline→revisedで途中への新規追加、章間移動、番号変更、本文変更、削除候補が期待差分に一致。番号だけで対応づけない。
- 変更なしの再読込で絵・音声・尺・カメラ・アンカー・話者・対応表が全て不変。
- 新規カットだけが空の絵プレースホルダーを持つ。素材付きの削除候補を勝手に消さない。
- ト書き2行は2動作、柱は場面情報、折返し台詞は1台詞。曖昧な話者/OFF/ナレーションは手動確認。
- 同じ番号、別作品の同じID、重複ID、未知の版、破損JSON、XSS文字列、容量超過、古い/分岐ファイルを安全に扱う。
- 受信側独自変更と競合すれば保留。差分表示・キャンセル不変・1回Undo/Redo・保存再起動後の対応保持を両アプリで確認。
- バックアップJSON/TXT/MDの既存用途を維持し、交換JSONをバックアップと誤認して上書きしない。
